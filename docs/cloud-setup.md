# บัญชีและการซิงก์ Supabase

แอปนี้ตั้งค่าโปรเจกต์ Supabase แยกชื่อ `bacc-exam-2569` แล้ว ผู้ใช้ใหม่กด **สร้างบัญชี** ตั้งชื่อที่ไม่ซ้ำและ PIN ตัวเลข 8–12 หลัก จากนั้นใช้งานได้ทันที การเข้าสู่ระบบจะถูกจำไว้บนเบราว์เซอร์เครื่องนั้น เมื่อเปลี่ยนเครื่องให้เข้าสู่ระบบด้วยชื่อและ PIN เดิม (ชื่อจะถูกปรับช่องว่างและตัวพิมพ์เล็ก/ใหญ่ให้ตรงกัน)

- ประวัติผลสอบ ข้อสอบที่ทำค้าง คำตอบ เวลาที่เหลือ ชุดข้อสอบ คลังที่นำเข้า และการตั้งค่าจะถูกบันทึกลงในเครื่องและซิงก์กับ Supabase โดยอัตโนมัติ ไม่จำกัดจำนวนผลสอบโดยตัวแอป
- รอจนแสดง **บันทึกขึ้นคลาวด์แล้ว** ก่อนปิดหรือเปลี่ยนเครื่อง การเชื่อมต่อสะดุดอาจทำให้ข้อมูลล่าสุดยังอยู่เฉพาะเครื่องเดิม ระบบจะลองซิงก์ใหม่อัตโนมัติ และแสดงข้อผิดพลาดที่หน้าแรกหรือขณะทำข้อสอบ
- หากแก้ไขบัญชีเดียวกันพร้อมกันหลายเครื่อง ระบบจะหยุดซิงก์แทนการเขียนทับข้อมูลอีกเครื่อง สามารถกลับไปใช้เครื่องที่ยังมีข้อมูลค้างแล้วเก็บข้อมูลนั้นไว้ หรือเลือก **ใช้ข้อมูลล่าสุดจากคลาวด์** ในเมนูบัญชี (จะทิ้งข้อมูลที่ยังไม่ซิงก์ของเครื่องนั้น) แนะนำใช้ทีละเครื่อง
- ประวัติจากเวอร์ชันเดิมที่เก็บอยู่บนเครื่องเดิมยังไม่ถูกลบ หลังเข้าสู่ระบบให้เปิดเมนูบัญชี เลือกโปรไฟล์เดิม และกด **นำเข้าประวัติจากเครื่องนี้** ก่อนรอให้ซิงก์สำเร็จ หากข้อมูลเก่าอยู่ใน GitHub/Firebase ต้องนำข้อมูลกลับลงเบราว์เซอร์ด้วยเวอร์ชันเก่าก่อน
- ต้องใช้อินเทอร์เน็ตเพื่อเข้าสู่ระบบและดึงข้อมูลเริ่มต้น PIN ไม่ถูกเก็บใน localStorage แต่ session และสำเนาข้อมูลถูกเก็บในเบราว์เซอร์ จึงควรออกจากระบบเมื่อใช้เครื่องร่วมกับผู้อื่น และการออกจากระบบไม่ได้ลบสำเนาข้อมูลในเครื่อง
- เมื่อสมัครสำเร็จ หน้าจอจะแสดงชื่อและ PIN ครั้งเดียวเพื่อให้แคปหน้าจอหรือบันทึกลงตัวจัดการรหัสผ่าน เก็บภาพไว้อย่างปลอดภัยและอย่าส่งต่อ เมื่อกดเข้าใช้งาน PIN จะไม่ถูกเก็บใน localStorage
- ชื่อเป็นชื่อสำหรับเข้าสู่ระบบแยกจากชื่อบนใบผลสอบ โปรดจำชื่อและ PIN: **ไม่มีระบบกู้ PIN ทางอีเมล** เลือก PIN ที่เดายากและไม่ใช้ซ้ำกับบริการสำคัญ การใช้ PIN มีความปลอดภัยต่ำกว่ารหัสผ่านที่แข็งแรง

## สำหรับผู้ดูแล

- โปรเจกต์: `oqigdiwdblppeombecyi` (Singapore); frontend ใช้ URL และ **publishable key** ใน `src/lib/supabase.js` ซึ่งไม่ใช่ secret และสามารถ override ด้วย `VITE_SUPABASE_URL` และ `VITE_SUPABASE_PUBLISHABLE_KEY` ตอน build ห้ามใส่ service-role key ใน frontend
- Auth ใช้ email/password ภายใน โดยแปลงชื่อที่ normalize แล้วเป็น SHA-256 เพื่อสร้างที่อยู่อีเมลภายใน `@accounts.bacc.invalid` ไม่ใช่อีเมลรับข้อความจริง และเปิด auto-confirm สำหรับโปรเจกต์แยกนี้ จึงไม่มีการกู้บัญชีผ่านอีเมล
- ตาราง `public.exam_user_state` และ RLS อยู่ใน `supabase/migrations/20261110000000_exam_user_state.sql` แต่ละบัญชีอ่าน/เพิ่ม/แก้ไขได้เฉพาะแถวที่ `user_id = auth.uid()` การซิงก์ใช้ revision เพื่อตรวจพบการแก้ไขพร้อมกัน
- ตารางรายชื่อเพื่อน สถิติสาธารณะ และห้องแข่งขันหลายคน (`public.friend_profiles`, `public.friend_matches`, `public.friend_match_players` พร้อม trigger ดึงรายชื่อบัญชีเดิมจาก `auth.users` และ `exam_user_state`) อยู่ใน `supabase/migrations/20261110010000_friend_arena.sql`
- Supabase Auth มีการจำกัดอัตราคำขอตามการตั้งค่าโครงการ แต่ PIN ที่คาดเดาง่ายยังเสี่ยงถูกเดา ควรติดตามการใช้งาน ตั้งค่า rate limit/CAPTCHA เพิ่มตามความเหมาะสม และใช้วิธีเข้าสู่ระบบที่แข็งแรงกว่านี้หากข้อมูลมีความอ่อนไหว
- ตรวจด้วย `npm test` และ `npm run build` การตั้งค่า URL/key อย่างเดียวไม่สร้างตารางหรือเปิด auto-confirm ให้โปรเจกต์ใหม่ ต้องใช้ migration และตั้งค่า Auth ด้วย

## รายชื่อเพื่อนในหน้า “แข่งขันกับเพื่อน” ขึ้นแค่ตัวเอง

การ์ด “แข่งขันกับเพื่อน” ดึงรายชื่อจาก 3 แหล่งรวมกัน

1. **คลาวด์ `public.friend_profiles`** — บัญชีทั้งหมดในระบบ (แหล่งหลัก)
2. **RPC `public.list_friend_directory()`** — ตัวสำรองที่อ่านจาก `auth.users` + `exam_user_state` ตรง ๆ ใช้เมื่อตารางข้างบนว่างหรือ backfill ไม่ครบ
3. **บัญชี/โปรไฟล์ที่เคยเข้าสู่ระบบบนเครื่องนี้** (`localStorage`)

ถ้าเห็นแค่บัญชีของตัวเอง ให้ดูข้อความสถานะใต้หัวข้อการ์ดก่อน

- `☁️ ซิงก์รายชื่อจากคลาวด์แล้ว · พบ N บัญชีในระบบ` = ปกติ จำนวน N คือจำนวนบัญชีที่ฐานข้อมูลตอบกลับมา
- `☁️ คลาวด์มีแค่บัญชีของคุณ` = ยังไม่มีแถวของคนอื่นในฐานข้อมูล ต้องรัน SQL ด้านล่างนี้
- `⚠️ ซิงก์รายชื่อไม่สำเร็จ: …` = แอปบอกสาเหตุตรง ๆ (ตารางหาย / RLS ไม่อนุญาต / เครือข่าย) ให้แก้ตามข้อความ
- `📱 ยังไม่ได้ซิงก์จากคลาวด์` = ยังไม่ล็อกอินหรือออฟไลน์ ระบบใช้รายชื่อที่บันทึกไว้ในเครื่อง

> **สถานะโปรเจกต์ `oqigdiwdblppeombecyi` (10 พ.ย. 2026):** ลง migration ครบแล้ว — ตาราง `friend_profiles`, `friend_matches`, `friend_match_players` (RLS 3 policies ต่อตาราง), trigger 2 ตัว, realtime publication และ RPC `list_friend_directory()` พร้อม backfill บัญชีทั้ง 4 บัญชีในระบบ
>
> สาเหตุเดิมที่ตารางไม่เคยถูกสร้าง: ไฟล์ `20261110010000_friend_arena.sql` สร้าง policy `friend_matches_update` ซึ่งอ้างตาราง `friend_match_players` **ก่อน** ที่ตารางนั้นจะมีอยู่ ทำให้ migration ล้มทั้งก้อนและ rollback → แอปเห็นแค่บัญชีของตัวเอง ลำดับถูกแก้แล้วในไฟล์ (สร้าง policy นี้หลังตาราง players) และใส่ `drop policy if exists` ให้รันซ้ำได้

### วิธีแก้ฝั่งฐานข้อมูล

รัน migration ให้ครบทั้งสองไฟล์ (ทำซ้ำได้ ปลอดภัย)

```sql
-- ใน Supabase SQL Editor
-- 1) supabase/migrations/20261110010000_friend_arena.sql
-- 2) supabase/migrations/20261110020000_friend_directory_rpc.sql
```

จากนั้นตรวจว่ามีรายชื่อครบ

```sql
select count(*) as accounts from auth.users;
select count(*) as directory_rows from public.friend_profiles;
select * from public.list_friend_directory() limit 20;
```

ถ้าจำนวนแถวใน `friend_profiles` น้อยกว่าจำนวนบัญชี ให้รันบล็อก backfill ในไฟล์ `20261110020000_friend_directory_rpc.sql` อีกครั้ง (ใช้ `on conflict do nothing` จึงไม่ทับข้อมูลเดิม) หรือกดปุ่ม **รีเฟรชรายชื่อ** ในหน้าเพื่อน ซึ่งจะเรียก RPC สำรองและเติมรายชื่อที่ขาดให้ทันที
